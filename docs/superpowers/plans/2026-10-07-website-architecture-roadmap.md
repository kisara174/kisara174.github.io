# 网站架构优化计划清单

> **For agentic workers:** 后续使用 executing-plans 按独立交付推进，主代理负责技术决策与验收。本文件是路线清单；涉及资源加载或主题行为的改动，执行前先根据实际接口细化该项实施步骤。

**Goal:** 保留 Hexo 静态架构，让网站加载更轻、主题更易维护，并用实际需求判断是否迁移。

**Architecture:** Markdown → Hexo + Fluid → 静态网页 → GitHub Pages + Cloudflare。近期优化浏览器收到的资源与主题适配方式，复用已有写作、发布、订阅和健康检查。Astro 仅列为条件性预览，不作为本阶段既定迁移目标。

**Tech Stack:** 当前 Hexo 8.1.1、Fluid 1.9.9；Node 版本以 `.nvmrc` 为准。

**Spec:** 本轮对话接受的架构建议，以及[性能测量记录](../../maintenance/performance.md)、[视觉验收记录](../../maintenance/visual-acceptance.md)和[第三阶段总清单](2026-10-04-website-phase3-plan.md)。

## 4：Astro 条件性预览与迁移判断

**启动条件：** 出现具体且持续的多布局需求（例如作品集、研究页面、项目详情），或主题覆盖已持续妨碍维护。单凭“第三方主题”或一次性能分数不足以启动迁移。

**范围：** 与正式站隔离的预览项目，仅做首页和一篇带公式长文章。启动前另写具体实施计划并限定目录、依赖和内容复用边界，本清单不创建项目或变更 Pages。

- [ ] 将真实页面需求写成示例，比较继续 Fluid、自有 Hexo 主题和 Astro 三种实现成本。
- [ ] 如 Astro 更合适，再做静态内容与必要交互的最小预览，不先搬迁全站。
- [ ] 检查 Markdown 数学语法、代码高亮、图片路径、日期/时区和全部原 URL 的兼容方案。
- [ ] 核对 Giscus pathname、canonical、RSS、sitemap、robots、搜索和系列导航的延续方式。
- [ ] 分别列出可沿用的部署/健康流程与必须适配的写作脚本、产物校验；不假定现有工具无需修改。
- [ ] 同内容、同条件比较视觉、性能、维护步骤和依赖数量，形成继续 Hexo 或迁移的明确决定。

**验收：** 预览足以支持决策，正式站不受影响。只有迁移收益明确、兼容方案完整，才进入全站迁移计划。
